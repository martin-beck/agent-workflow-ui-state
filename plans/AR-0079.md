# AR-0079: Remote token resolution and single-use completion

Complete the remote launcher path after dynamic issuance. A user on another
Linux, Windows, or macOS machine must resolve the token through the configured
SSH alias, fetch exactly the bound request, run the GUI when available (or the
equivalent TUI), and return only validated final events to the authoritative
host. A token remains retryable after cancellation or transport failure, but
becomes atomically consumed only after the complete batch is accepted and the
event journal is durably persisted.

Acceptance:

- launcher resolves the registry over SSH using the user's OpenSSH config,
  validates host/project/session/revision/packet digest, and never constructs
  routing paths from the opaque token;
- request fetch, local GUI/TUI execution, event upload, journal validation, and
  token consumption form one observable success protocol with bounded cleanup;
- cancellation, partial save, UI crash, SSH failure, stale request, and failed
  upload leave the token active for safe retry and leave no accepted partial
  commitment;
- successful completion atomically marks the token consumed and replay attempts
  fail closed, including concurrent two-client races;
- tests cover real local SSH server round trips for GUI and TUI, including
  retry, replay, expiry, concurrency, and hostile path/alias cases.
