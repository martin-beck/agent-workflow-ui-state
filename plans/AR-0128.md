# AR-0128: Android decision interaction parity

Make the Android renderer a complete decision-taking client for the shared
revision-bound batch contract. It must preserve the TUI/GUI action semantics,
show structured proposal information, keep unanswered actions unanswered, and
never claim an authoritative save when no batch was delivered or when the
service rejected an event.

## Scope

- select, reject, clarify, request-more-evidence, reopen, and safe-exit;
- structured user proposals (label, rationale, confidence, trade-offs) with
  editing before commitment;
- batch progress, incomplete/unsaved exit handling, and Save+Exit;
- protocol/event tests for accepted, rejected, retried, and revision-bound
  actions, plus Android JVM/UI coverage.

## Acceptance evidence

- Every action maps to the existing Android bridge event vocabulary and is
  revision/session/device bound.
- Clarify, reject, and evidence requests leave the decision unresolved;
  reopen makes an answered decision editable again.
- Save is reported only after a real batch exists and all required events are
  accepted or durably journaled.
- Structured own proposals round-trip in the event payload and can be edited.
- JVM and Compose tests cover multi-decision partial batches and exit states.
